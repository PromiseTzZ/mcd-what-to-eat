# 目的

帮用户解决"吃什么"的选择困难：基于麦当劳 MCP（mcd-mcp）的真实菜单、营养与优惠券数据，按时段（早餐/正餐/下午茶）给出五档推荐——最低卡、最省钱、兼顾、惊喜、自由组合。默认只推荐，绝不自动下单。

> 本文的工具名省略客户端前缀。Qoder / Claude Code 是 `mcp__mcd-mcp__query-meals`，DSH 是 `mcp__mcd__query-meals`，其他客户端可能不带前缀——一律按**后缀**匹配，不要按前缀判断是否已接入。

# 前置检查（先于一切调用）

1. 工具列表中存在 `query-meals` / `calculate-price` / `list-nutrition-foods` 任一个 → 已接入，继续。
2. 都没有 → 输出下面三行后停止，不要假装能推荐：

   > 需要先接入麦当劳 MCP（免费）：
   > ① 打开 open.mcd.cn/mcp，手机号登录 → 控制台 → 激活并复制 Token
   > ② 添加 MCP：Streamable HTTP，地址 `https://mcp.mcd.cn`，Header `Authorization: Bearer <Token>`
   > ③ 装好后回来说"今天中午吃什么"

   再问一句"你用的是哪个客户端？"，按 `references/setup.md` 给对应步骤；用户不回答就不展开。
3. 401 → Token 无效或过期，让用户重新复制；429 → 限流（600 次/分钟），建议稍后再试，不要连续重试。

# 工具调用契约（实测，别猜）

- 门店类工具（query-meals / query-meal-detail / calculate-price / query-store-coupons）三个必填：
  `storeCode`、`orderType`、`beType`。`beType`：1 到店取餐 / 2 麦乐送 / 5 得来速 / 6 团餐。
- **到店自取（orderType=1 且 beType=1）不要传 `beCode`**，传了会报错；外送、得来速、团餐才需要，
  值取自 query-nearby-stores / delivery-query-stores 的返回。
- query-nearby-stores 没有经纬度参数，只有 `city` + `keyword`，靠 `searchType=2` 按位置搜索
  （`searchType=1` 是搜收藏门店）。用户说"我在武汉江汉路"→ city=武汉、keyword=江汉路。
- `reservationDate`（yyyy-MM-dd HH:mm）只在预约场景传，非预约不传。

# 时段判定

- 默认调 now-time-info 取当前时段（早餐/午餐/下午茶等），按该时段过滤菜单。
- 用户明说"早餐/下午茶/晚餐"→ 以用户为准；用户问"中午吃什么"→ 按午餐处理。
- 时段只用于选品和提示，**某品是否在售一律以 query-meals 实际返回为准**，不要硬编码门店换餐时间。

# 工作流

1. **定门店**：用户给了位置 → query-nearby-stores（`searchType=2`，`city`+`keyword`）取最近 1~2 家；没给 → 先问一句（有常用店可直接用）。到店取餐 `beType=1`，得来速 `beType=5`；外送走 delivery-query-addresses → delivery-query-stores。
2. **拉菜单**：query-meals 拿套餐与单品列表，按时段过滤；只对候选前几名用 query-meal-detail 补详情，不全量拉取。
3. **取热量（三级溯源，命中即停，输出标来源）**：
   - **A 官方精确值**：list-nutrition-foods 无入参，一次返回约 160 条**单品**（不含套餐）。格式为表头 `[N]{productName,nutritionDescription,energyKj,energyKcal,protein,fat,carbohydrate,sodium,calcium}:` 加逐行 `名称,null,千焦,千卡,蛋白质,脂肪,碳水,钠,钙`——**取第 4 列 energyKcal，不要用千焦**。数据无餐品编码，只能按名称匹配；套餐 = 组成子品逐项相加。个别条目热量为 0（多为饮品），不是缺数据。若 query-meal-detail 直接返回营养字段，优先用它。
   - **B 官方渠道补查**：A 匹配不到 → 联网检索麦当劳中国官方来源（mcd.cn 官网营养信息页、官方小程序商品页）。只采纳能给出**单品**数值且**能记录 URL** 的结果；套餐仍按子品相加。
   - **C 折算估算**：A、B 都拿不到 → 用营养库同品类、近规格条目折算（例："王牌炸鸡任选2" ≈ 麦辣鸡翅 224×2 至 麦麦脆汁鸡 330×2 → 写 ≈450–660；新品汉堡参照同规格汉堡区间；饮料按 0–225 kcal 计）。**必须写成 ≈区间或约数，并注明折算基准。**
   - **D 确实无据**：以上都失败 → 写"官方未提供营养数据"，并说明已尝试 A/B/C。不留空、不编造。
   - 同一候选有多个来源时取最高级，A/B 值优先参与排序；某档结论若完全依赖 C 级估算，该档标"（估算）"。
   - 联网能力不可用 → 跳过 B，直接 C。每档联网补查最多 3 个品。
4. **拿券**：available-coupons + query-store-coupons；用户已登录可加 query-my-coupons。记录每张券的门槛（满减金额/限定品类/限定时段）。不自动领券。
5. **算价**：候选组合一律用 calculate-price 实算券后价，不心算；券门槛不满足时换下一张券再算。
6. **生成五档推荐**（全部来自上述真实数据，档与档之间尽量不重复）：
   - 🥗 **最低卡**：热量已知者中最低；并列取券后价低。
   - 🎫 **最省钱**：券后价最低；并列取热量低。
   - ⚖️ **兼顾**：在帕累托最优集合（没有别的候选热量和价格都更优）中，取加权评分最低者（热量、券后价各占 50%，先各自归一化）。
   - 🎲 **惊喜**：从其余候选中随机挑一个，附一句值得一试的理由（限定新品/口感/活动联动），避免与前三档重复。
   - 🧩 **自由搭（非套餐）**：从单品/小食中组合"主食 + 饮料或小食"（如 汉堡单品 + 派/饮料），calculate-price 实算券后价，与最便宜套餐对比并突出优势（"比最低价套餐再省 X 元"或"热量约为其一半"）。
7. **输出**（保持精简）：
   一张对比表：档位 | 内容 | 原价 | 券后价 | 用的券 | 热量 | 一句理由。
   热量列带来源上标：A 写 `620¹`，B 写 `620²`，C 写 `≈450–660³`，D 写 `未提供⁴`；表下用一两行脚注说明每级来源（B 必须附链接，C 必须写折算基准）。
   再补最多两三句：最划算的券怎么用、时段提醒（如"早餐还剩 XX 分钟"）。
8. **可选约束**：用户给了预算上限/热量上限/忌口/份数 → 先过滤候选再选档。热量上限过滤只用 A/B 值；仅 C 级数据的候选不参与该过滤，避免估算值误杀。
9. **收尾**：问一句"要下单吗？"仅当用户明确回复下单，才调用 create-order；最终价格以 create-order 返回为准。

# 硬约束

- 未经用户明确确认，禁止调用 create-order / cancel-order。
- 热量必须可溯源，按 A→B→C→D 取值并标注：A 精确值 / B 官方值并附 URL / C 估算（≈ 区间或约数 + 折算基准）/ D 明说缺失并注明已试过的来源。禁止凭空编造看似精确的单值，禁止留空。
- 券后价必须来自 calculate-price 实算，禁止模型心算。
- 输出最多一张表 + 两三句说明，不罗列全菜单、不贴原始接口返回。
